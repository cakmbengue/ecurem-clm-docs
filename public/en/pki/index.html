Client PKI

Build and operate a private certification hierarchy per organization: root, intermediate and issuing authorities, profiles, CSR requests, issued certificates, revocation, CRL, OCSP and audit.

1. What the module provides

The Client PKI dashboard groups certification authorities, issued certificates, revoked certificates and post-quantum authorities for your organization. Main interface actions include New Managed Root, Import an Offline Root, New Child Authority, New Profile and Submit a CSR.

PKI objects are isolated by organization. A request cannot use a profile or authority owned by another organization.

2. Choose the PKI hierarchy

Ecurem CLM distinguishes three authority types:

  • Root: self-signed trust anchor.
  • Intermediate: signed by a root and used to separate trust layers.
  • Issuing: authority intended to sign end-entity certificates.
Important rule: an issuing authority cannot sign another authority. An intermediate authority may only create an issuing authority. When the PKI issuing-CA control is enabled, end-entity certificates must be issued by an Issuing authority.

A common hierarchy is Root → Intermediate → Issuing → End-entity certificates.

3. Create a managed root

From Client PKI, select New Managed Root. The form asks for:

  • Organization.
  • Name: internal display name.
  • X.509 Common Name.
  • Signature algorithm.
  • Validity in days: from 365 to 7300; the initial value is 3650 days.
  • CRL distribution URL.
  • OCSP URL.

After creation, Ecurem CLM creates the self-signed root, protects the private key in the configured backend, generates an initial CRL and prepares an OCSP responder.

4. Import an offline root

Use Import an Offline Root when the root is created and kept outside Ecurem CLM. The platform can reference the root certificate and build the operational hierarchy without holding that root private key.

This model is useful when policy requires an offline trust anchor. Daily issuance can then be delegated to an intermediate or issuing authority.

5. Create a child authority

Select New Child Authority. Fields are:

  • Organization.
  • Parent authority: active, non-revoked root or intermediate from the same organization.
  • Authority type: Intermediate or Issuing.
  • Name.
  • X.509 Common Name.
  • Signature algorithm.
  • Validity in days: from 30 to 3650, initially 1825 days.
  • CRL distribution URL for issued certificates.
  • OCSP URL for issued certificates.

The actual child validity cannot exceed the parent’s remaining lifetime. The platform also enforces X.509 path-length and CA constraints.

6. Create a certificate profile

Select New Profile and configure:

  • Organization.
  • Name.
  • Validity in days.
  • Allowed DNS suffixes: one per line.
  • Allow wildcards.
  • Require approval.
  • Enabled.

In the current customer interface, the technical usages are initialized for TLS server certificates with digitalSignature and serverAuth.

7. Submit a CSR

The Submit a CSR form asks for exactly:

  • Organization.
  • Profile.
  • Authority.
  • CSR PEM.

The CSR must be valid PKCS#10 PEM, have a valid cryptographic signature, contain a Common Name and comply with the selected profile. Common Name and Subject Alternative Names are parsed from the CSR.

8. Approval and issuance

Request states include Pending, Approved, Rejected, Issued and Failed.

If the profile requires approval, the request must be explicitly approved before issuance. The authority must be enabled, non-revoked and in the same organization. When the issuing-CA requirement is enabled, the selected authority must be of type Issuing.

After issuance, Ecurem CLM stores the serial number, certificate PEM, chain, SHA-256 fingerprint, validity dates and source request.

9. Revocation, CRL and OCSP

Revocation records include the reason, revocation time and actor. The module also maintains signed CRLs, delegated OCSP responders and PKI audit events containing organization, actor, action, object, outcome and useful details.

Before production use, ensure public CRL and OCSP URLs are correctly defined and reachable by relying systems.

10. Available algorithms

  • RSA 3072
  • RSA 4096
  • ECDSA P-256
  • ECDSA P-384
  • ML-DSA-44
  • ML-DSA-65
  • ML-DSA-87

Select algorithms according to cryptographic policy and relying-party compatibility. Post-quantum support should be validated end to end before operational use.

11. Common errors

  • Profile belongs to another organization: use a profile from the request organization.
  • Authority belongs to another organization: use an authority from the same tenant.
  • Invalid PKCS#10 PEM CSR: fix PEM formatting or regenerate the CSR.
  • Invalid CSR signature: regenerate the request from the original private key.
  • CSR has no Common Name: include a CN in the CSR.
  • Authority is not offered: check enabled/revoked state and Issuing type requirement.
  • Request remains pending: check whether explicit approval is required.
